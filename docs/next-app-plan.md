# 다음 단계: 하단 탭 첫 전환 최적화

> 상태: 계획 (2026-08-15)

## 배경

배포 환경에서 하단 탭을 처음 열 때 짧은 대기가 있다. 현재 앱의 주요 화면은 사용자 인증과 Supabase 조회가 필요한 동적 라우트라, 기본 `Link` 프리패치만으로는 전체 화면 데이터가 미리 준비되지 않는다.

지연은 스켈레톤이 필요할 정도로 길지 않다. 비활성 화면의 상태를 보존하는 keep-alive도 첫 방문 속도에는 영향을 주지 않으므로 도입하지 않는다.

## 목표

하단 내비게이션이 보이는 동안 다섯 탭의 기본 경로를 백그라운드에서 미리 준비해 첫 탭 전환을 빠르게 만든다.

```text
지도 / → 기록 /records → 장소 /places → 사람 /people → 설정 /settings
```

## 구현

1. `BottomNavigation`의 각 `Link`에 `prefetch={true}`를 지정한다.
2. Next.js가 제공하는 링크 프리패치만 사용하고 별도 `useEffect`, `router.prefetch`, 전역 상태는 만들지 않는다.
3. 현재 탭은 기존처럼 `usePathname`과 `aria-current="page"`로 표시한다.
4. 검색 조건, 페이지 번호, 상세·작성·수정 경로는 미리 불러오지 않는다. 각 탭의 기본 URL만 대상이다.

## 예상 비용과 기준

- 초기 화면 렌더링을 막지는 않지만, 사용자가 누르지 않은 탭의 인증과 Supabase 조회도 실행된다.
- 개인 기록 서비스의 현재 데이터 규모와 다섯 개의 고정 탭에서는 허용 가능한 비용으로 판단한다.
- 목록 데이터가 커지면 프리패치를 제거하기 전에 기록·사람·장소 목록의 페이지네이션 또는 무한 스크롤을 먼저 검토한다.
- 첫 방문 문제이므로 keep-alive, React `Activity`, Next.js `cacheComponents`는 범위에서 제외한다.
- 지연이 짧으므로 `loading.tsx`와 탭별 스켈레톤도 추가하지 않는다.

## 완료 조건

- 배포용 프로덕션 빌드에서 하단 탭 링크의 RSC 요청이 클릭 전에 시작된다.
- 각 탭을 처음 눌렀을 때 현재보다 빠르게 실제 콘텐츠가 표시된다.
- 프리패치 중에도 현재 화면의 렌더링과 조작이 막히지 않는다.
- 기록 추가·수정·삭제 후 관련 탭을 열면 재검증된 데이터가 보인다.
- 상세·작성·수정 화면에서는 하단 탭 프리패치 요청이 발생하지 않는다.

## 검증

1. 프로덕션 빌드를 실행하고 로그인한다.
2. 개발자 도구 Network에서 `_rsc` 요청을 확인한다.
3. 하단 내비게이션이 보이면 현재 탭을 제외한 기본 경로가 클릭 전에 요청되는지 확인한다.
4. 각 탭의 첫 클릭 시 URL, 활성 아이콘, 실제 콘텐츠가 자연스럽게 전환되는지 확인한다.
5. 기록을 변경한 뒤 지도·기록·장소 탭에서 오래된 프리패치 결과가 남지 않는지 확인한다.
