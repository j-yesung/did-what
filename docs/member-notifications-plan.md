# 알림함 개선 TODO

구성원별 앱 내부 알림 기능의 구현 세부사항은 코드와 마이그레이션을 기준으로 관리한다. 이 문서는 현재 구현된 내용을 반복하지 않고, 운영·품질·확장을 위해 남은 결정과 작업만 기록한다.

## 우선순위

### P0 — 데이터 보관과 운영 안정성

- [ ] **알림 보관 상한 확정**
  - 수신 구성원별 알림을 최대 50개까지 보관한다.
  - 새 알림 저장 시 오래된 읽은 알림부터 정리한다.
  - 50개가 모두 읽지 않은 상태일 때의 정책을 결정한다. (상한을 일시적으로 초과하거나 가장 오래된 미읽음도 정리)
  - 기록 생성과 같은 트랜잭션에서 수행할 정리와, 정기 작업에서 수행할 정리를 구분한다.
  - 정리 작업이 동시 기록 생성에서 중복 실행돼도 안전하고, 기록 생성 트랜잭션을 오래 점유하지 않는지 검증한다.

- [ ] **정기 정리 작업 추가**
  - 오래된 읽은 알림과 삭제된 기록의 알림을 주기적으로 정리한다.
  - Supabase Cron 또는 별도 운영 작업 중 프로젝트 운영 방식에 맞는 방법을 선택한다.
  - 작업 재실행이 안전하도록 삭제 범위를 제한하고 실행 결과를 기록한다.

- [ ] **푸시 구독 정리**
  - 만료·거부된 endpoint(예: 404/410 응답)를 저장소에서 제거한다.
  - 같은 구성원·기기의 중복 구독을 방지한다.
  - 구성원 전환이나 로그아웃 뒤 이전 구독이 남지 않는지 확인한다.
  - 푸시 실패가 기록 및 앱 내부 알림 저장을 막지 않는지 계속 검증한다.

- [ ] **운영 모니터링**
  - 기록 생성, 알림 bulk insert, 읽음 처리, 보관 정리, 푸시 발송의 성공·실패를 구분해 추적한다.
  - 알림 생성 수와 대상 구성원 수가 맞지 않는 경우를 감지한다.
  - 푸시 실패율과 만료 endpoint 증가를 확인할 수 있는 로그·알람을 마련한다.

### P1 — 중복과 사용자 경험 개선

- [ ] **중복 알림 방지**
  - 동일 기록이 같은 수신 구성원에게 두 번 생성되지 않도록 DB 제약 또는 RPC의 멱등 처리를 검토한다.
  - 재시도·네트워크 중복 요청 상황을 포함해 검증한다.

- [ ] **알림 이동 실패 처리**
  - 기록이 삭제됐거나 접근할 수 없을 때 현재 화면에 머물며 이유를 안내한다.
  - 오래된 알림을 눌렀을 때의 안내 문구와 재시도 동작을 정한다.

- [ ] **목록 최신성 정책 점검**
  - 포커스 복귀 시 갱신하는 현재 정책이 충분한지 실제 사용 패턴으로 확인한다.
  - 필요성이 확인될 때만 수동 새로고침 또는 Realtime을 도입한다.
  - 읽음 처리 후 목록·배지 캐시가 모든 탭에서 즉시 일치하는지 확인한다.

- [ ] **접근성·실기기 점검**
  - 배지의 색상 대비, 실제 개수와 `9+` 표시의 접근성 이름을 확인한다.
  - 벨·알림 행·뒤로가기 스와이프를 iOS Safari와 Android Chrome에서 확인한다.
  - 긴 기록 제목, 삭제된 기록, 빈 목록, 오류, 추가 불러오기 상태를 확인한다.

### P2 — 기능 확장

- [ ] **알림 종류 확장**
  - 두 번째 알림 종류가 필요해지는 시점에만 `notification_type` 도입을 검토한다.
  - 종류별 제목·이동 대상·읽음 정책을 먼저 정의하고 범용 payload 도입 여부를 결정한다.

- [ ] **알림 그룹화**
  - 알림 수가 많아지면 날짜별 구분이나 같은 기록에 대한 알림 묶음을 검토한다.
  - 그룹화가 커서 페이지네이션과 읽음 처리에 미치는 영향을 함께 확인한다.

- [ ] **알림 설정**
  - 알림 종류별 수신 여부와 푸시 수신 여부를 분리해 설정할지 결정한다.
  - 앱 내부 알림은 유지하고 OS 푸시만 끄는 선택지를 우선 검토한다.
