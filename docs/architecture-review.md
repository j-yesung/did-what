# 프로젝트 구조 후속 개선

- 검토일: 2026-09-09
- 범위: 아직 완료하지 않은 구조·성능 개선
- 원칙: 완료한 작업은 문서에 보관하지 않고 Git 이력에서 확인한다.

## 1. 기록에 포함된 장소마다 같은 검색을 반복한다

### 근거

- [resolve-record-location.ts](../src/features/record/select-record-location/api/resolve-record-location.ts)는 Kakao 장소를 항목별로 다시 검색한다.
- 기존 장소 DB 조회는 일괄 처리하지만, 같은 검색 결과에서 고른 Kakao 장소는 검색 요청이 중복될 수 있다.

### 개선 방향

검색어·페이지·검색 범위가 같은 항목을 묶어 한 번씩 검증한다. 서버에서 선택 항목을 검증하는 절차는 유지한다.

### 확인 사항

검색 범위가 같은 항목만 합치고, 요청 수가 장소 수가 아니라 검색 그룹 수에 비례하는지 측정한다.

## 2. 푸시 발송 완료까지 기록 저장 응답이 기다린다

### 근거

- [create-record.ts](../src/features/record/create-record/api/create-record.ts)는 기록 저장 후 `sendRecordPush()`를 기다린다.
- 푸시 서비스가 느리면 DB 저장이 끝난 뒤에도 완료 응답이 지연된다.

### 개선 방향

Next.js `after()`를 사용해 푸시를 응답 이후 작업으로 옮긴다. 배포 환경의 실행 시간 제한과 실패 로그는 유지한다.

### 확인 사항

푸시 지연·실패가 기록 저장 응답 시간과 저장 결과에 영향을 주지 않는지 확인한다.

## 3. 지역 정의와 지도 계산의 책임이 섞여 있다

### 근거

[korea-map.ts](../src/entities/region/model/korea-map.ts)는 행정구역 정의·코드 변환, GeoJSON 경계 처리, 격자 생성, 방문 집계를 함께 담당한다. 전국·지역별 격자도 모듈을 불러올 때 생성한다.

### 개선 방향

실제 번들 비용을 측정한 뒤 지역 정의·코드 변환과 지도 계산을 분리한다. 격자 사전 계산은 측정 결과가 필요할 때만 도입한다.

## 적용 원칙

- 요청 최적화 전후의 요청 수와 응답 시간을 비교한다.
- 파일은 줄 수가 아니라 변경 이유와 책임이 갈릴 때 분리한다.
- 각 작업 전 현재 호출처를 다시 확인한다.
- 코드 변경 후 검증은 [검증 가이드](./verification.md)를 따른다.
