# 기록 상세 댓글 구현 계획

작성일: 2026-09-14
상태: 구현 및 연결된 DB migration 적용 완료
범위: 저장소 코드·migration·DB 테스트 구현과 연결된 Supabase DB 적용.

## 1. 목표와 권장 범위

기록 상세에서 같은 계정의 멤버들이 각자의 이름으로 댓글을 남길 수 있게 한다. 기록 작성자가 아닌 멤버도 작성할 수 있으며, 댓글 작성자는 현재 선택된 활성 멤버로 결정한다.

사용자의 확정 요구는 **기록 상세 댓글과 멤버 단위 작성**이다. 아래 글자 수, 정렬, 수정·삭제 정책은 구현을 구체화하기 위한 제안 기본값이다.

| 항목 | 1차 구현 제안 |
| --- | --- |
| 작성·조회 | 같은 계정의 활성 멤버가 기록에 댓글 작성, 같은 계정 내 댓글 공유 |
| 수정·삭제 | 현재 선택된 멤버가 작성한 댓글에만 제공 |
| 내용 | 일반 텍스트, 줄바꿈 허용, 앞뒤 공백 제거 후 1~1,000자 |
| 목록 | 최신순, 최초 20개, 명시적인 ‘이전 댓글 더 보기’ |
| 표시 | 멤버 이름, 본인 표시, 작성 시각, 수정 여부, 내용 |
| 기록 삭제 | 연결된 댓글도 함께 영구 삭제 |
| 알림 | 댓글을 최초 등록할 때만 작성자를 제외한 활성 멤버에게 인앱 알림 저장 및 푸시 발송. 수정·삭제 시 미발송 |
| 제외 | 대댓글, 반응, 첨부, 멘션, 실시간 구독, 댓글 수의 목록 노출 |

새 라이브러리나 별도 전역 상태는 도입하지 않는다. 기존 Supabase 클라이언트, 멤버 세션, React Query, 서버 액션과 공용 UI를 사용한다.

## 2. 현재 구조와 중요한 제약

### 멤버는 공유 계정 안의 프로필이다

- `src/entities/member/api/member-session.ts`의 `requireMember()`가 로그인 계정, 계정 소속 멤버, `did-what-member` HttpOnly 쿠키, 활성 여부를 검증한다.
- `account_members.owner_id`는 Supabase Auth 사용자 ID다. 멤버마다 별도 로그인이나 JWT가 발급되지는 않는다.
- `selectMember()`는 같은 계정의 활성 멤버로 전환할 수 있으며 레이아웃을 재검증한다.
- 기록에는 `author_member_id`가 있지만 기존 기록 수정·삭제 권한은 계정 단위다. 댓글 때문에 기존 기록 권한을 바꾸지 않는다.
- 푸시 구독은 현재 선택된 멤버에 귀속된다. 댓글 작성자의 구독과 비활성 멤버의 구독은 발송 대상에서 제외한다.

따라서 **계정 간 데이터 격리는 DB RLS로 보장하고, 선택 멤버 기준 작성·수정·삭제는 서버 액션에서 검증**한다. UI에서 버튼만 숨기는 방식으로 끝내지 않는다.

다만 공유 계정 사용자는 다른 멤버로 직접 전환할 수 있다. 동일 계정 JWT만으로 DB가 브라우저의 현재 선택 멤버를 구분할 수도 없다. ‘본인 댓글만 수정’은 현재 프로필 기준의 제품 동작이지, 같은 계정 사용자 사이의 독립된 신원·보안 경계가 아니다. RPC에 멤버 ID를 넘기는 것만으로도 이 한계는 해결되지 않는다.

향후 멤버 간 위조 방지까지 요구한다면 멤버별 인증과 계정 참여 관계 설계부터 변경해야 한다. 현재 요구는 기존 공유 계정 모델을 유지하는 것으로 해석한다.

### 기록 상세와 캐시

- `src/pages/record/detail/index.tsx`는 기록 ID만 검증해 클라이언트 상세 화면에 전달한다.
- `record-detail-content.tsx`는 목록에서 캐시한 기록 요약이 있으면 방문 장소만 추가 조회하고, 없으면 기록 상세를 조회한다.
- 댓글을 기존 상세 조회 결과에 끼워 넣으면 이 두 진입 경로에서 댓글 로딩 여부가 달라진다. 별도 댓글 쿼리를 둬 양쪽 경로에서 동일하게 동작시킨다.
- `MAIN_QUERY_OPTIONS`는 60초 staleTime과 창 포커스 재조회를 사용한다. 댓글은 별도 staleTime 0으로 재진입·창 포커스 시 재조회하되 캐시된 내용을 먼저 보여준다. 열린 화면 간 즉시 동기화는 1차 범위가 아니다.
- 로그아웃은 기존 `queryClient.clear()`를 재사용한다.

## 3. 화면과 사용자 동작

기록 제목·방문 장소·메모 다음, 기록 삭제 버튼 위에 댓글 영역을 배치한다. 메모가 없어도 댓글 영역은 표시한다.

1. ‘댓글’ 제목 아래에 현재 멤버 이름과 입력 폼을 표시한다. 예: ‘예성으로 댓글 남기기’.
2. 입력은 공용 `Textarea`, 제출은 공용 `Button`을 사용한다. Enter는 줄바꿈으로 유지해 한글 조합 중 오등록을 방지한다.
3. 등록 성공 후 서버가 반환한 댓글을 목록 위에 반영하고 입력을 비운다. 실패하면 입력을 그대로 보존하고 재시도를 제공한다.
4. 각 댓글에는 작성자와 시각을 표시한다. 작성자 ID와 현재 멤버 ID가 같을 때만 수정·삭제 동작을 노출한다.
5. 수정은 해당 댓글 안에서 진행하고 저장·취소를 제공한다. 삭제는 공용 `ConfirmDialog`로 확인한다.
6. 기록 삭제 확인 문구에 ‘댓글도 함께 삭제됩니다’를 추가한다.
7. 각 댓글 행에 `comment-{commentId}` DOM id를 부여해 알림 링크의 해시 이동을 지원한다.

### 상태와 레이아웃

- 최초 조회 중: 댓글 영역에만 로딩 표시. 기록 본문을 가리지 않는다.
- 댓글 없음: ‘이 기록에 첫 댓글을 남겨보세요’와 입력 폼 표시.
- 조회 실패: 영역 내 오류와 다시 시도. 기존 댓글 캐시가 있으면 유지한다.
- 제출 중: 제출 동작과 해당 입력만 잠그고 버튼 크기·문구를 유지한다. 전체 댓글 목록을 스피너로 교체하지 않는다.
- 댓글이 많음: 페이지 자체 스크롤과 더 보기 사용. 중첩 스크롤은 두지 않고, 자동 스크롤은 댓글 알림의 해시 진입에만 사용한다. 대상이 첫 페이지에 없으면 찾을 때까지 다음 페이지를 조회한다.
- 긴 URL·공백 없는 문자열: `min-w-0`, 줄바꿈과 단어 넘침 처리를 적용한다.
- 모바일 키보드: 입력 폼을 하단 고정 내비게이션과 겹치지 않는 문서 흐름에 둔다.
- 접근성: 입력 label, 오류 연결, 삭제 버튼의 댓글 식별 이름, 등록 결과 안내와 삭제 후 포커스 복구를 제공한다.

작성·수정·삭제는 `useOptimistic`으로 즉시 반영하고 `useTransition`이 서버 요청의 pending 상태를 관리한다. React Query를 서버 기준 상태로 유지하며 성공 시 해당 기록의 댓글 캐시만 확정한다. 실패하면 optimistic 상태를 자동 롤백하고, 작성 초안이나 수정 폼을 복원한다. 버튼을 스피너나 다른 문구로 교체하지 않아 전환 중 레이아웃 깜빡임을 막는다.

## 4. 데이터 모델

새 `public.record_comments` 테이블을 추가한다.

| 컬럼 | 제안 타입·제약 | 용도 |
| --- | --- | --- |
| `id` | uuid, PK | 댓글 식별자. 새 작성 시 UUID를 생성하고 같은 요청 재시도에 재사용 |
| `owner_id` | uuid, NOT NULL, auth.users FK | 계정 격리 기준, 계정 삭제 시 cascade |
| `record_id` | uuid, NOT NULL | 대상 기록 |
| `author_member_id` | uuid, NOT NULL | 작성 멤버 |
| `body` | text, NOT NULL | 정규화한 본문, DB CHECK로 공백만 있는 내용·길이 제한 검증 |
| `created_at` | timestamptz, NOT NULL, default now() | 생성 시각·페이지네이션 기준 |
| `updated_at` | timestamptz, NOT NULL, default now() | 최종 수정 시각·수정 충돌 판정 |

### 관계와 인덱스

- `(owner_id, author_member_id)` → `account_members(owner_id, id)` 복합 FK. 기존 멤버 테이블의 UNIQUE 제약을 사용해 다른 계정 작성자 연결을 막는다.
- `records(owner_id, id)`에 복합 UNIQUE를 추가하고 `(owner_id, record_id)` 복합 FK로 참조한다. 다른 계정 기록 연결을 DB에서도 막고 기록 삭제 시 댓글을 cascade 삭제한다.
- 멤버 삭제는 참조가 남아 있으면 제한한다. 기존 활성/비활성 모델을 유지하며 비활성 멤버의 과거 댓글도 표시한다.
- 조회 인덱스는 `(owner_id, record_id, created_at desc, id desc)`. 작성자 FK 지원 인덱스는 `(owner_id, author_member_id)`를 둔다.
- 기존 `public.set_updated_at()` 트리거 함수를 재사용한다. 작성·수정 시각과 작성자는 클라이언트 입력값을 그대로 저장하지 않는다.
- 작성자 이름은 멤버 테이블에서 조회한다. 이름 변경 시 과거 댓글에도 현재 이름이 표시되는 정책이며 이름 스냅샷은 추가하지 않는다.
- 기존 기록의 데이터 backfill은 필요 없다. `records`의 UNIQUE 인덱스 생성에 필요한 시간과 잠금은 적용 전 데이터량 기준으로 확인한다.

### 알림 데이터 확장

기존 `notifications` 테이블은 기록 생성 알림 한 종류만 가정하며 `(record_id, recipient_member_id)`가 UNIQUE다. 댓글마다 별도 알림을 저장하려면 다음과 같이 확장한다.

| 변경 | 제안 |
| --- | --- |
| 알림 종류 | `event_type` 추가: `record_created`, `comment_created`. 기존 행은 `record_created`로 backfill 후 NOT NULL·CHECK 적용 |
| 댓글 연결 | nullable `comment_id` 추가, `record_comments(id)` FK와 `ON DELETE SET NULL` 적용 |
| 기록 알림 중복 방지 | 기존 UNIQUE 제약을 제거하고 `event_type = 'record_created'`인 `(record_id, recipient_member_id)` partial UNIQUE index로 대체 |
| 댓글 알림 중복 방지 | `event_type = 'comment_created' and comment_id is not null`인 `(comment_id, recipient_member_id)` partial UNIQUE index 추가 |
| 조회 | 기존 수신자 커서 인덱스를 유지하고 알림 조회 컬럼에 `event_type`, `comment_id` 추가 |

`sender_name`과 `record_title`은 기존처럼 알림 생성 시점의 스냅샷을 사용한다. 댓글 본문은 알림 테이블과 푸시 payload에 복제하지 않는다. 잠금 화면 노출을 줄이고, 수정·삭제 후 오래된 문구가 남는 문제를 피하기 위해서다.

댓글이 삭제되면 새 알림을 만들지 않고 기존 알림의 `comment_id`만 FK 동작으로 null이 된다. 알림 이력은 남으며 인앱 알림은 ‘삭제된 댓글이에요’를 표시한다. 기록이 남아 있으면 기록 상세로 이동하고, 기록까지 삭제되면 기존 정책대로 `record_id`도 null이 되어 이동을 비활성화한다.

### 권한

새 테이블에 RLS를 활성화하고 grants를 명시한다. 계정 격리 정책과 접근 권한은 함께 설정해야 한다. [Supabase RLS 공식 문서](https://supabase.com/docs/guides/database/postgres/row-level-security)

| 경로 | 검증 |
| --- | --- |
| SELECT | `authenticated`이며 `owner_id = (select auth.uid())` |
| INSERT | 로그인 계정 일치, 같은 계정 기록·멤버 연결, 작성 멤버 활성 여부 |
| UPDATE | 기존 행에 대한 계정 검증과 변경 결과 검증을 모두 적용. 본문 컬럼만 수정 허용 |
| DELETE | 로그인 계정 소유 행만 허용 |
| 서버 액션 | 매 요청 `requireMember()` 호출. 수정·삭제 SQL에 현재 멤버 ID 조건 추가 |

`anon`에는 접근을 허용하지 않는다. INSERT는 필요한 입력 컬럼만, UPDATE는 `body`만 허용해 ID·계정·기록·작성자·시각의 변경을 차단한다. UPDATE에는 SELECT 정책도 필요하다. 트리거가 `updated_at`을 관리한다.

이 설계에서 인증된 동일 계정의 직접 Data API 호출은 계정 권한을 갖는다. 서버 액션의 현재 멤버 제한을 DB가 동일하게 보장한다고 문서화하거나 테스트하지 않는다. 이를 보장해야 한다면 앞서 설명한 인증 모델 변경을 선행한다. 불필요한 service-role 클라이언트나 SECURITY DEFINER RPC는 추가하지 않는다.

## 5. 조회·서버 액션·캐시

### 조회

- 상세 페이지 서버에서 `requireMember()`를 호출해 `ownerId`와 현재 멤버의 최소 정보(id, name)를 전달한다. 기존 인증 검증의 요청 내 캐시를 재사용한다.
- 댓글은 브라우저 Supabase 클라이언트로 조회한다. 계정·기록을 필터링하고 RLS가 최종 계정 접근을 제한한다.
- 작성자 이름은 FK 관계로 함께 조회해 댓글별 추가 요청을 만들지 않는다. 비활성 작성자를 조회에서 제외하지 않는다.
- `(created_at, id)` 내림차순 커서로 21개를 읽고 20개와 다음 커서를 반환한다. 같은 시각 댓글도 안정적으로 정렬한다.
- 댓글 쿼리 키: `['record-comments', ownerId, recordId]`. 개인별 권한은 캐시된 `isMine` 값 대신 현재 멤버 ID로 계산한다.
- 기록 존재 여부가 확인된 경우 댓글 영역을 활성화한다. 기록 요약 캐시만 남은 경우 실제 기록 조회 결과와 맞춰 제거한다.

### 작성·수정·삭제

- `createComment`: 댓글 UUID, 기록 UUID, 본문, 화면이 알고 있는 멤버 ID를 받는다. 멤버 ID는 전환 감지용 기대값이며 실제 작성자는 서버의 `requireMember()`에서 결정한다.
- 기대 멤버와 서버 멤버가 다르면 등록하지 않고 화면 갱신을 안내한다. 다른 탭에서 멤버를 바꿨을 때 입력 내용이 다른 이름으로 저장되는 것을 막는다.
- 공개 `create_record_comment` RPC는 SECURITY INVOKER로 댓글을 저장하고, 기존 기록 생성 흐름과 같은 방식으로 private 알림 함수가 수신자별 인앱 알림을 만든다. 댓글과 인앱 알림을 하나의 DB 트랜잭션으로 처리해 둘 중 하나만 저장되는 상태를 만들지 않는다.
- private SECURITY DEFINER 함수가 필요하면 `private` 스키마에 두고 PUBLIC·anon 실행 권한을 회수한다. 함수 내부에서 `auth.uid()`, 기록 소유권, 활성 작성자 멤버를 다시 검증한다.
- `updateComment` / `deleteComment`: 계정·기록·댓글·현재 작성자 멤버 조건을 모두 포함한다. 수정·삭제 시 기존 `updated_at`도 비교해 다른 탭의 변경을 덮어쓰지 않는다.
- `updateComment`와 `deleteComment`는 알림 생성 함수와 푸시 발송 함수를 호출하지 않는다. 수정 내용 알림, 삭제 알림, 재알림은 만들지 않는다.
- UUID, 입력 타입, 공백, 길이를 서버에서 다시 검증한다. 길이 기준은 Unicode code point로 통일해 JS UTF-16 길이와 DB `char_length` 차이를 테스트한다.
- RPC는 댓글 결과와 `created` 여부를 반환한다. Server Action 반환 형식은 기존 `status`, `message` 형태에 댓글 결과와 이 값을 추가한다. 영향 행이 0개면 성공으로 처리하지 않고 없음·권한 변경·수정 충돌에 맞는 복구 안내를 제공한다.
- 동일 UUID의 등록 재시도는 기존 행의 계정·기록·작성자·본문이 일치하는지 확인한 뒤 기존 결과를 돌려준다. 응답만 유실됐을 때 중복 댓글을 만들지 않으며, UUID 충돌을 핑계로 기존 내용을 덮어쓰지 않는다.

### 갱신과 전환

- 기존 `useActionMutation`은 성공 시 invalidate하고 결과 콜백을 실행하는 형태다. 성공 후 갱신만 필요하면 재사용한다.
- 서버 결과의 즉시 캐시 반영과 네트워크 실패 시 폼 상태 제어가 필요하면 댓글 전용 `useMutation`에서 처리한다. 공용 훅을 댓글만을 위한 옵션으로 확장하지 않는다.
- 성공 결과를 ID 기준으로 캐시에 병합하거나 삭제하고 해당 기록 댓글 키만 invalidate한다. 작성·수정에 기록 목록, 지도, 장소 전체 재조회는 필요 없다.
- 새 댓글 삽입과 더 보기 경계에서 ID 중복을 제거하고 서버 재조회 결과로 페이지를 정합화한다. 갱신 실패를 저장 실패로 오인해 재등록하지 않는다.
- `revalidatePath('/records/[실제 ID]')`가 필요하더라도 이것만으로 React Query가 갱신된다고 가정하지 않는다.
- 멤버 변경 시 댓글 입력·수정 폼을 `member.id` 기준으로 리셋한다. 댓글 데이터는 공유하지만 초안·처리 중 상태는 다음 멤버에게 넘기지 않는다.
- 기록 삭제 성공 시 해당 댓글 캐시도 제거한다. 댓글이 독립 쿼리 키이므로 기존 `RECORDS_QUERY_KEY` invalidate만으로는 지워지지 않는다.
- 기록이 다른 탭에서 삭제됐다면 FK 실패/조회 결과를 처리하고 댓글 입력을 중단한다. 기존 데이터가 없는 기록에 댓글만 남지 않아야 한다.

### 인앱 알림과 푸시

- 알림 이벤트의 유일한 발생 시점은 새 댓글의 최초 INSERT다. 댓글 UPDATE·DELETE는 알림 발생 조건이 아니다.
- 수신자는 댓글 작성자를 제외한 같은 계정의 활성 멤버 전체다. 한 멤버가 여러 기기를 등록했다면 해당 멤버의 모든 유효한 구독으로 푸시한다.
- 같은 댓글 UUID 재시도는 `(comment_id, recipient_member_id)` UNIQUE index로 수신자별 알림도 중복 생성하지 않는다.
- 댓글 작성 Server Action은 RPC가 새 댓글을 만들었다고 반환한 경우에만, RPC 성공 후 기존 푸시 발송 흐름을 호출한다. DB 커밋 전에는 푸시하지 않는다.
- 기존 `sendRecordPush`의 구독 조회, VAPID 설정, 404·410 구독 정리 로직을 공통 내부 함수로 추출하고 기록·댓글별 title, tag, URL만 전달한다.
- 댓글 푸시 tag는 `comment-{commentId}`, URL은 `/records/{recordId}#comment-{commentId}`로 한다. 서로 다른 댓글 알림이 OS에서 하나로 덮어써지지 않는다.
- 푸시는 부가 기능이므로 VAPID 설정 누락이나 외부 푸시 서비스 실패가 댓글 성공 결과를 바꾸지 않는다. 실패는 기존 방식대로 서버 로그에 남기고 만료 구독만 정리한다.
- 푸시는 외부 서비스 특성상 정확히 한 번 전달을 보장하지 않는다. 같은 댓글은 동일 tag로 표시해 재전달되더라도 OS 알림이 누적되지 않게 하고, 인앱 알림의 정확한 중복 방지는 DB UNIQUE index가 담당한다. 전달 보장이 필요해질 때만 outbox와 재시도 작업을 추가한다.
- 현재 알림 목록은 창 포커스 시 다시 조회한다. 실시간 구독은 추가하지 않으며, 푸시를 받은 열린 앱의 배지 즉시 갱신이 필요해질 때 서비스 워커 메시지 연동을 별도 검토한다.

#### 알림 문구 예시

기록 제목이 ‘성수에서 저녁’, 댓글 작성자가 ‘예성’인 경우를 기준으로 한다.

| 위치 | 문구 | 비고 |
| --- | --- | --- |
| 인앱 알림 첫 줄 | `예성님이 댓글을 남겼어요` | 조사 처리를 위해 이름 뒤에 항상 ‘님이’ 사용 |
| 인앱 알림 둘째 줄 | `성수에서 저녁` | 기존 알림과 같이 기록 제목 표시 |
| 푸시 제목 | `예성님이 댓글을 남겼어요` | 잠금 화면에 댓글 본문은 표시하지 않음 |
| 삭제된 댓글 보조 문구 | `삭제된 댓글이에요` | 기록이 남아 있으면 상세 이동 가능 |
| 삭제된 기록 보조 문구 | `삭제된 기록이에요` | 기존 동작 유지, 이동 비활성화 |

접근성 이름은 읽음 여부와 이동 가능 상태까지 포함한다. 예: `읽지 않은 알림, 예성님이 댓글을 남겼어요, 성수에서 저녁 기록 보기`.

## 7. 구현 순서와 완료 조건

1. **스키마·권한**: 구현 환경의 실제 스키마와 migration 이력을 비교하고 댓글·알림 migration을 생성한다. 격리된 로컬 DB에 적용해 FK, grants, RLS, 알림 중복 방지와 cascade를 먼저 검증한다.
2. **데이터 접근·액션**: DB 타입을 갱신하고 댓글 쿼리·커서·입력 검증·멤버 검증·재시도와 인앱 알림 생성을 구현한다.
3. **상세·알림 UI**: 현재 멤버 전달, 댓글 작성·조회·수정·삭제와 알림 목록의 이벤트별 문구·링크를 연결한다.
4. **푸시**: 기존 기록 푸시를 공통 발송부로 정리하고 댓글 푸시를 연결한다. 서비스 워커 payload 형식은 유지한다.
5. **캐시·회귀**: 직접 진입/목록 진입, 멤버 전환, 중복 제출, 다중 탭, 알림 읽음, 기록·댓글 삭제와 로그아웃을 검증한다.
6. **배포**: 기존 앱과 호환되는 추가형 DB 변경을 먼저 적용하고 앱을 배포한다. 배포 전 migration dry-run과 접근 권한 진단을 확인한다.

앱 롤백 시 댓글 UI·액션을 이전 버전으로 되돌리되 이미 쌓인 댓글 테이블은 보존한다. DB DROP을 기본 롤백으로 사용하지 않는다.

코드 구현 후 `docs/verification.md`에 따라 관련 Node 테스트와 DB 권한 테스트를 실행한다. `pnpm exec biome check --write src app`, `pnpm lint`, `pnpm exec tsc --noEmit`을 수행하고, 이번 구현은 서버 액션·서버/클라이언트 경계를 변경하므로 `pnpm build`도 실행한다. DB 테스트는 관리자 성공만 확인하지 말고 실제 `anon`/`authenticated` 역할과 서로 다른 계정으로 수행한다.

구현 후 Biome, lint, TypeScript 검사와 전체 Node 테스트를 통과했다. 기본 Turbopack 빌드는 실행 환경의 프로세스·포트 제한으로 실패했지만, 동일 코드의 Webpack 프로덕션 빌드는 통과했다. DB migration은 연결된 Supabase 프로젝트에 `20260914064953_record_comments`로 적용했고, 테이블·RPC·알림 함수·RLS와 정책 4개가 생성된 것을 확인했다. pgTAP 테스트는 작성했으나 로컬 환경에 Docker/Podman이 없어 아직 실행하지 못했다. Supabase RLS 공식 문서는 확인했으며, changelog 원문은 현 세션에서 markdown content-type 문제로 확인하지 못했다.
